# ADR-012 Semantic Search with Embedded LanceDB Index

## Контекст
`search_notes` у [[Vault MCP Server]] (ПР № 3) шукав за ключовими словами: підрядок у назві, aliases, тегах і тілі, а агенту повертав назву й один рядок до 200 символів. Нотатки vault — українською з англійськими назвами, тож питання своїми словами чи англійською («taste profile», «edit the knowledge base files») не знаходили [[Preference Profile]] чи [[ADR-005 Separate Vault Repository with MCP Access]]. Коли нотатку знаходили, рядка-сніпета не вистачало для відповіді. ПР № 7 вимагає вдосконалити той самий інструмент векторним пошуком за embeddings, не додаючи нового каналу доступу до vault. Обмеження: мінімум інфраструктури ([[ADR-001 Layered Architecture]], [[ADR-002 SQLite with better-sqlite3]]: без зовнішніх сервісів), а в ADR-005 «Chroma як сервер» вже відхилено як зайву інфраструктуру.

## Рішення
- **Embeddings** — `Xenova/multilingual-e5-small` (int8, 384 виміри) через `@huggingface/transformers` 4.3.0, обчислюються локально. Модель (~145 МБ) завантажується один раз у `harness/vault-mcp/.index/models/`. Префікси e5 `query:` / `passage:`.
- **Сховище** — `@lancedb/lancedb` 0.39.0 в embedded-режимі (бібліотека в процесі сервера, без окремого сервера): `harness/vault-mcp/.index/lancedb/`, у `.gitignore`. Vault лишається джерелом істини, індекс — похідний артефакт. Окрема таблиця на модель, тож зміна моделі не змішує вектори.
- **Chunking** — розділ `##` нотатки. Довгі розділи діляться на межах абзаців до 1200 символів (e5 читає до 512 токенів). Текст для embedding — «назва (aliases) — розділ» + текст розділу.
- **Актуальність** — перед кожним пошуком сервер звіряє sha1 тексту нотаток і повторно вбудовує лише змінені; видалені нотатки прибирає. Сервер індексує у фоні після підключення. `npm run reindex` перебудовує все.
- **Інструмент** — та сама сигнатура `search_notes(query, type, tag, limit)`. Результат — N найближчих фрагментів: `title`, `path`, `type`, `section`, `score` (косинусна близькість), `snippet` (текст розділу до 700 символів). Фільтри `type` і `tag` виконуються в LanceDB.
- **Резерв** — пошук за ключовими словами: `VAULT_SEARCH=keyword` або автоматично, якщо модель чи індекс недоступні.
- Код: `harness/vault-mcp/src/semantic.ts`, `config.ts`, `reindex.ts`.

## Альтернативи
- **`sqlite-vec` у `better-sqlite3`** — менше нових залежностей (застосунок уже на SQLite), фільтри звичайним SQL. Відхилено на користь LanceDB як найближчого Node-аналога embedded Chroma з умови ПР № 7.
- **Chroma** — JS-клієнт потребує окремого сервера Chroma; суперечить ADR-005.
- **Python `sentence-transformers`** — другий рантайм поруч із Node.js сервера.
- **Хмарний API embeddings** — ключ, мережа, нотатки залишають машину.
- **Англомовна модель `all-MiniLM-L6-v2`** (~23 МБ) — слабка на українському тексті.
- **Нотатка цілком як фрагмент** — довгі ADR розмиваються й перевищують 512 токенів.
- **Гібрид BM25 + вектори** — для 38 нотаток не потрібен; варто повернутися, якщо запити за ідентифікаторами (`FR-4`, `watches.movie_id`) почнуть програвати.

## Наслідки
- Порівняння на 10 питаннях (`docs/rag-evaluation/`): нотатка з відповіддю першою 10/10 проти 6/10, MRR 1.0 проти 0.67. Агент лише з `search_notes` дав 10 повних відповідей проти 4 повних, 5 часткових і 1 без відповіді; вигаданих фактів 0 в обох режимах. Planner (ПР № 6) на FR-8 склав рівноцінні плани — він навігує через [[MOC]] і `get_note`.
- Skills і ролі оркестрації отримали кращий пошук без змін у своїх файлах.
- Перший запуск завантажує модель (~145 МБ). Індексація 38 нотаток займає ~10 с, embedding запиту — мілісекунди.
- Відповіді довші: ~$0.01 більше на відповідь агента.
- Перевіряють тести `harness/vault-mcp/test/semantic.test.ts` (chunking, інкрементальна синхронізація, фільтри, перезапуск) і `vault.test.ts` («falls back to keyword search when semantic search fails»). Відтворення порівняння — `npm run eval`.

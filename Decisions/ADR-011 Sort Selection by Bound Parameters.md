# ADR-011 Sort Selection by Bound Parameters

## Контекст
NFR-3 — лише параметризовані запити; skill `new-module` (крок 5) забороняє будь-який SQL зі складених рядків, а знайдене grep-перевіркою треба виправляти, а не пояснювати. Але [[ADR-010 Watch History Query Contract]] вимагає вибору поля й напряму сортування, а SQLite не дозволяє передати ім'я стовпця чи `ASC`/`DESC` як параметр. План оркестрації (ПР № 6) пропонував складати `ORDER BY` з константної мапи (`HISTORY_FROM + HISTORY_WHERE + ORDER_BY[sort][order]`); Coder відхилив це як порушення правила, Reviewer погодився. Друга сила — `total` має завжди відповідати відфільтрованим записам (NFR-1: фільтри й пагінація в SQL у [[Repositories Layer]]).

## Рішення
- **Сортування — параметри, а не текст SQL.** Поле й напрям приходять із закритих Zod-переліків (`WatchSort`, `SortOrder`), прив'язуються як `@sort`/`@order` і обираються термами `CASE WHEN @sort = 'rating' AND @order = 'desc' THEN w.rating END DESC` в одному фіксованому запиті — по одному терму на пару «поле × напрям», далі терми tie-break і завжди `w.movie_id`. Для неактивної пари `CASE` дає NULL і не впливає на порядок.
- **Сторінка й підрахунок — два повні літеральні запити** (`HISTORY_PAGE_SQL`, `HISTORY_COUNT_SQL` у `src/repositories/watch-repository.ts`) з однаковим блоком `WHERE`, записаним двічі; спільний фрагмент заборонений, бо його довелося б конкатенувати.
- **Розходження двох `WHERE` ловлять тести:** допоміжна функція `titles()` у `test/watches.test.ts` перевіряє `total === items.length` для кожного фільтра. Мутаційна перевірка (інвертування кожного порівняння лише в `COUNT`) — кожна мутація валить тест.
- Конвенція для всіх майбутніх списків із сортуванням.

## Альтернативи
- **Константна мапа `ORDER BY` + конкатенація** (план, D5/D10) — користувацький текст у SQL не потрапляє, але це складання SQL, яке заборонене правилом і ламає grep-перевірку; якщо перелік колись послабиться — ризик ін'єкції.
- **Окремий фіксований запит на кожне сортування** (8 штук) — `WHERE` повторюється 8 разів замість 2.
- **Один запит із CTE і `LEFT JOIN` для `total`** — без дублювання `WHERE`, але складніший; Reviewer запропонував як запасний варіант.
- **Сортування в пам'яті** — порушує NFR-1 (пагінація має бути в SQL).

## Наслідки
- Сортування не використовує індекс (SQLite будує тимчасове B-дерево). Виміряно: p95 ≈ 7 мс на 10 000 фільмів і переглядів при бюджеті 200 мс (`test/watch-history.perf.test.ts`). Переглянути, якщо межа каталогу NFR-1 суттєво зросте.
- Невідоме значення `@sort` (якщо перелік послаблять) дає лише порядок за `movie_id`, а не ін'єкцію.
- Зміна фільтра потребує правки обох `WHERE`; тест із `total` впаде, якщо оновити лише один.
- Сортування за назвою — бінарний порядок `title_key` ([[ADR-008 Unicode Case-Insensitive Keys in App Layer]]): і/ї/є/ґ після решти кирилиці.
- Репозиторії можуть ділитися SQL-помічниками (`genresByMovie` з `movie-repository.ts` використовує `WatchRepository`); [[ADR-001 Layered Architecture]] це дозволяє.
